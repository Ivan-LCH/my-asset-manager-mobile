> 개정 2: [07. 현재 자산 관리·은퇴설계](07-current-assets-and-retirement.md)를 함께 적용한다. 제품 목적·현재 자산 기능 보존·홈·현황과 전망의 분리는 07이 우선하며, AM-01~AM-10·C01~C29과 R0 기준선을 추가한다. 나머지 계산·저장 계약은 이 문서를 유지한다.

작성일: 2026-09-14. 대상: `Ivan-LCH/my-asset-manager-mobile`, 분석 기준 커밋 `053f83ec698d74fa37ba2280b00ee8a4ba388a1c`.

이 문서는 기존 분석을 구현 작업으로 옮기는 **통합 적용 기준**이다. 사용자 유형별 화면·계산 적용 범위·저장 계약·도입 순서의 추가 결정은 이 문서를 우선한다. 코드 결함의 근거는 [01](01-current-review.md), 계산 구조는 [02](02-domain-and-engine.md), UX 상세는 [03](03-experience-design.md), 기존 인수 테스트 A01~A30은 [04](04-delivery-and-acceptance.md)를 함께 사용한다.

재건축은 조건부 부동산 기능이다. 재건축 자산이 없는 사용자에게 재건축 카드·일정·비교안을 표시하지 않는다. 첫 구현도 공통 은퇴 흐름과 부동산 없는 사용자를 포함해야 한다. 시제품의 사용자 유형 선택기는 검토용이며 실제 제품에서 사용자가 ‘재건축형’ 같은 유형을 직접 고르게 하지 않는다.

## 1. 이번 보완의 범위와 완료 모습

사용자는 현재 자산·부채를 독립적으로 관리하고, 원할 때 가구·수입·생활비·예정 사건을 입력해 은퇴설계를 시작한다. 은퇴 입력 없이 시세 갱신·계좌/종목 상세·이력·배당을 사용할 수 있다. 현황과 전망은 기준일을 명시하며 같은 원천 revision에서 요약과 상세를 생성한다.

## 2. 사용자별 기능 노출 규칙

### 2.1 ‘없음’과 ‘아직 모름’을 먼저 구분

각 입력 영역에 `unknown | confirmedNone | provided`를 저장한다. 자산 테이블이 비었다는 이유만으로 “부동산이 없다”거나 “세금이 없다”고 판단하지 않는다. `unknown`이면 홈에 작고 명확한 확인 과제를 제공하고, 해당 영역이 결과에 중요한 경우 분석을 부분 결과로 표시한다. `confirmedNone`이면 해당 기능의 빈 카드와 반복 입력 권유를 숨긴다.

개별 금액·날짜에는 `known | estimated | unknown`과 출처·기준일을 둔다. 0원은 사용자가 확정적으로 0을 입력하거나 규칙이 0을 산출한 경우에만 숫자 0으로 처리한다. 잘못된 문자열, 미입력, 조회 오류를 0으로 정규화하지 않는다.

### 2.2 노출을 결정하는 함수

```ts
type Availability = {
  featureId: string;
  state: 'available' | 'needsInput' | 'notApplicable';
  reasonCode: string;
  entityIds: string[];
  eventIds: string[];
};

deriveAvailability(snapshot, scenario, context): Availability[]
// context = { asOfDate, selectedPeriod, view: 'home' | 'assets' | 'plan' | 'analysis' }
```

이 함수는 UI에서 제멋대로 `assets.some(...)`를 반복하는 대신 공통으로 사용한다. 입력·계획에서는 미래 사건과 종료된 계약 이력에 접근할 수 있게 하고, 분석은 선택 기간에 해당하는 원장·상태만 반영한다. 화면에서 카드를 숨기는 결정과 계산에 원장 항목을 포함하는 결정은 분리한다. 현재 재건축이 끝났어도 과거 기간의 공사·분담금 내역을 제거하면 안 된다.

부동산 부재는 모든 세금·건강보험 부재를 뜻하지 않는다. 세금 요약은 실제 과세 대상 소득·거래·잔여 납부 의무로 결정한다. 부동산 매각 이후라도 아직 납부하지 않은 관련 세금·반환할 보증금은 남는다.

## 3. 전체 화면 수정안

### 3.1 공통 탐색과 상세

하단 탭을 `홈 / 자산 / 계획 / 분석`으로 구성한다. 설정·백업·데이터 관리·도움말은 홈 상단 설정으로 접근한다. 기존 링크는 새 화면의 동일 의미 위치로 리다이렉트한다.

| 화면/기존 파일 | 새 역할 | 구현 시 주의 |
|---|---|---|
| `Dashboard.tsx` | 현재 총자산·순자산·구성·갱신 상태 + 별도 계획 요약 | 계획 미입력에도 현재 관리 사용. 미래 추정과 현재 평가를 같은 KPI로 혼합하지 않음 |

| `PensionSimPage.tsx`, `CorpSimPage.tsx` | 같은 스냅샷을 쓰는 고급 전략 뷰 | 가구 외부/내부 자금과 법인 자체 잔액 구분 |
| `Settings.tsx` | 가구·표시·백업·규칙·앱 데이터 관리 | 중요 계획 입력을 설정에만 숨기지 않음 |

숫자 클릭 동작은 동일한 규칙을 쓴다: KPI → 구성 목록 → 원천 자산·사건 → 입력·산식·규칙 → 수정 → 영향 미리보기 → 적용 → 원래 결과 복귀. 분석 상세는 `runId + metricId`로 식별한다. 원천 편집 후에는 이전 run을 조용히 바꾸지 않고 새 run으로 교체됐음을 표시한다.

URL 예: `/analysis?scenario=base&year=2031&metric=cash.end`. 기본안·연도·상세 상태는 URL과 동기화하며 잘못된 ID는 오류 또는 유효한 기본 경로로 이동한다. 금액·주소·생년월은 URL에 넣지 않는다. 공유 URL만으로 다른 기기의 개인 데이터가 열리는 것처럼 안내하지 않는다.

### 3.2 홈

상단은 현재 자산 기준일·시세 갱신 상태다. 현재 자산의 준비 상태와 계획의 `추정 결과 있음 / 정보 확인 필요 / 계산 실패`를 분리한다. 준비되지 않은 계획으로 “안전한 은퇴”를 표시하지 않되 현재 자산 사용을 막지 않는다.

표시 순서: 현재 총자산·부채·순자산·현금 → 자산 구성과 주식 관리/갱신 진입 → 별도 은퇴 전망 또는 계획 시작 안내 → 관련 예정 사건. 현재 자산과 장래 연금 예상액의 현재가치를 섞지 않는다. 계획 미입력만으로 현재 자산 KPI를 숨기지 않는다.

### 3.3 계획

기본 섹션은 가구/은퇴, 반복 수입, 생활비, 일회성 사건, 공통 가정이다. 재건축·임대·연금·대출은 해당 조건에서만 추가 섹션으로 펼친다. 하나의 사건은 자산 상세와 계획에서 같은 ID를 편집한다.

생활비는 필수/선택, 월/연 금액, 적용 시작/종료, 물가 가정을 가진다. 이미 은퇴한 사용자는 현재 생활비를 중심으로 보여준다. 의료비 ‘적립’과 ‘실제 소비’를 구분하여 적립금이 자산으로 남는지 명시한다. 적립과 향후 의료 지출을 동시에 소비로 두 번 차감하지 않는다.

### 3.4 분석

공통 KPI: 세후 반복 수지 월평균, 기말 생활자금, 최초 자금 부족월, 인출 가능 자산/순자산. 데이터가 불완전한 KPI는 `— / 확인 필요`를 표시하고 누락 항목으로 연결한다. 계산 가능한 부분은 부분 결과로 제공하되 무조건 낙관적인 총평을 생성하지 않는다.

연도별 추이는 실제 계좌 잔액 집계로 만든다. 월 상세에서 세금·분담금·대출 상환 등 특정 월의 유출을 확인한다. 미래 소득, 계좌 원금 인출, 자산 매각대금, 신규 차입을 서로 다른 항목으로 보여준다. 지출·세금의 월평균 표시와 실제 납부월을 구분한다.

### 3.5 빈 상태·오류·접근성

`loading`에서는 이전 완료 결과 또는 skeleton을 표시한다. `failed`에서는 오류와 재시도, 이전 결과의 기준일을 표시한다. `notApplicable`은 관련 카드를 숨기고, `needsInput`은 입력 경로가 있는 안내를 표시한다. 지출이 아직 0원으로 입력됐다고 “생활비 평생 충당”을 판정하지 않는다.

카드·버튼 최소 44px 목표, 본문 16px 시작점, 단위·증감 기호·명확한 대비, 차트의 표 대체, dialog 초점 가두기·복귀·닫기 이름, 모바일 키보드와 safe-area를 인수 기준에 포함한다. 실제 대비·터치·스크린리더 품질은 실기기 검증으로 확인한다.

## 5. 계산·저장 기술 계약

### 5.1 단일 원천

`loadSnapshot()`은 필수 조회가 모두 준비된 후 같은 읽기 트랜잭션에서 계획·자산·계좌·계약·가정을 수집한다. 브라우저 현재 시각은 호출부에서 `asOfDate`로 한 번 전달한다. 조회 기간 시작일은 성장률 기준일이 아니다.

`validateSnapshot()`은 참조ID, 소유 지분, 기간, 금액, 분배 합계, 계좌 제한, 종료된 자산의 사건을 검사한다. 결과는 `blockingErrors`, `missingInputs`, `warnings`로 구분한다. 경고는 영향을 받는 KPI ID를 갖는다.

`simulate(snapshot, scenario, rules)`가 사건·상태·월별 원장·세금 납부·계좌별 잔액을 한 번 생성한다. 모든 **미래 전망 영역**은 선택 snapshot/run의 `selectOverview`, `selectYear`, `selectMonth`, `selectMetric`, `selectComparison`으로 읽는다. 현재 자산 영역은 별도 현재 `assetRevision`의 읽기 모델을 사용한다. 홈에서 두 기준을 구분하며 최신 시세 갱신이 과거 전망을 덮어쓰지 않는다. UI가 세금을 다시 계산하거나 pensionSchedule을 별도로 호출해 숫자를 바꾸면 안 된다.

### 5.2 보완해야 할 계산 계약

- 지급 목표와 실제 지급, 부족액을 분리한다. 음수 계좌를 0으로 잘라내면서 수입을 유지하지 않는다.
- 부족분 충당은 승인된 인출 정책에 따른다. 자동 주택 매각·자동 대출로 결과를 개선하지 않는다.
- 원천세는 한 번만 현금 차감하고 정산 세금은 기납부액을 반영한다. 미지원 세무는 금액 미확정으로 반환한다.
- 실제 투자원금·부채·공적 지급권을 구분한다. 같은 경제적 계좌를 두 자산 유형에서 중복 합산하지 않는다.
- 사건 발생일·과세 판단일·귀속기간·실제 납부일을 별도 값으로 유지한다.
- 연금·건보·세금은 실제 사람과 가입/납부 단위에 귀속한다. 사람 수를 ‘부부 2명’으로 고정하지 않는다.
- 의료 적립·퇴직금 배분·보증금·계좌이체는 소비 또는 소득과 구분한다.
- 결과에는 `runId`, `inputRevision`, `ruleVersions`, `assumptions`, `dataQuality`와 원천 추적 인덱스를 포함한다.

### 5.3 저장

```ts
savePlanPatch({
  planId,
  expectedRevision,
  changes: [{ entityId, field, value }],
}): Promise<{ revision: number }>
```

초안은 입력 도중 보관하되 분석은 유효한 저장 revision을 사용한다. revision 충돌 시 최신 값을 재조회하고 충돌 필드를 안내한다. 저장 실패 시 초안을 보존한다. 계산 중 추가 저장이 발생하면 최신 revision 결과만 활성화한다. 늦게 완료된 예전 계산이 화면을 덮어쓰면 안 된다.

현재 소스의 `Record<string, any>` 입력을 새 도메인 경계의 검증된 입력으로 점진 교체한다. 기존 IndexedDB row를 UI 전체에 직접 전달하기보다 어댑터에서 도메인으로 변환한다.

### 5.4 규칙·수동 예상액

이번 보완안은 새로운 세율이나 공제 기준을 확정하지 않는다. 기존 문서의 공식 출처를 시작점으로 구현 시 적용연도와 지원 범위를 검증한다. 수동 예상액은 `scope(세목/자산/개인/가구)`, 기간, 금액, 납부일, 근거, 작성일을 가진다. 동일 범위의 자동 추정과 합산하지 않고 명시적으로 대체한다. 부분 대체는 남은 범위를 보여준다.

규칙이 갱신되면 기존 완료 run은 보존하고 새 run으로 차이를 보여준다. 미래 규칙 유지 가정은 확정 제도로 표시하지 않는다.

원천 자산 삭제·사건 취소로 시나리오 참조가 깨지면 그 시나리오를 보존하되 ‘원천 수정 필요’로 표시한다. 조용히 기본안으로 바꾸거나 낙관적인 0원 결과를 만들지 않는다.

| R5 화면·비교 전환 | `App.tsx`, `AppLayout.tsx`, `Sidebar.tsx`, 페이지·공통 상세 컴포넌트 | 공통 4탭, 조건부 섹션, 드릴다운, URL 상태, 적용 가능한 시나리오 | 전망 KPI/상세는 선택 run, 현재 자산은 assetRevision 내부 합계 일치. 뒤로가기·미저장·미입력 검증 |
| R6 데이터 이전·출시 | `db.ts`, `Settings.tsx`, PWA 업데이트·문서 | migration 미리보기·버전 보존·복원 검사·전환 배포, 구 README 정정 | 원본 백업, 변환 합계 검증, 실패 복구, 실기기 확인 |

R1에서도 기존 금액이 맞는지 확인한 뒤 수정한다. 코드만 보고 제안한 발견 사항은 실행 가능한 환경에서 먼저 재현한다. 라이브러리 설치가 필요하면 현재 세션의 ‘추가 설치 없이 진행’ 선호를 존중하고 별도 요청 없이 설치하지 않는다.

### 완료되지 않은 기능의 처리

전환 중인 새 엔진은 ‘기능 누락 상태’에서 기존 결과와 섞어 하나의 완성된 전망을 만들어서는 안 된다. 지원 범위가 충족된 계획만 새 엔진을 활성화하거나, 명시적으로 부분 결과를 제공한다. 법인·복잡한 세무는 고급/미지원 상태로 남기더라도 현재 데이터와 기존 화면 접근을 보존한다.

## 10. 개발 인계 시 전달할 것

기본 인계 파일은 [전체 개선 개발 요청서](DEVELOPMENT-REQUEST.md), [07의 개정 기준](07-current-assets-and-retirement.md)과 이 문서다. 화면 참조를 위해 `docs/redesign/` 폴더 전체를 함께 전달하며, 개발 도구에는 [적용 작업 지시문](IMPLEMENTATION-PROMPT.md)을 사용할 수 있다. 전체 화면은 `full-app.html`과 [06의 대응표](06-full-app-walkthrough.md)를 기준으로 한다. R0 현재 기능 기준선 이후 R1부터 적용하며, 각 묶음에서 변경 파일·검증 결과·지원 범위·남은 항목을 기록한다. 시제품은 UX 참조이며 숫자 계산 코드를 제품 엔진으로 복사하지 않는다.

실제 부동산·연금 세무의 예외는 사용자 자료 또는 검증 가능한 규칙이 필요할 때 목록으로 남긴다. 사용자 선호에 영향을 주지 않는 파일 구조·컴포넌트 분할은 구현자가 결정해 진행한다. 가정이 필요한 경우 결과에 표시하고, 누락 정보를 조용히 사실로 확정하지 않는다.

이번 산출물은 적용 명세와 예시 화면이다. 실제 앱 기능·DB migration·세법 엔진을 적용 완료한 상태는 아니다.

## 11. 이번 보완안의 확인 기록

- 설치 없이 기존 Node로 시제품의 전체 JavaScript 문법을 확인했다.
- 5개 입력 완료 예시 × 기본/대안 2개 × 3년 = 30개 연도 행의 현금 증감식과 유한 숫자를 확인했다.
- 재건축 이외 예시의 사건 목록에 준공·분담금이 없고, 은퇴 1인 예시의 추가 사건 목록과 미입력 예시의 계산 결과가 비어 있음을 확인했다. 이는 데이터 함수 검사이며 브라우저 화면 자동화 검증은 아니다.
- 문서 내 로컬 링크 27개가 존재하는 파일을 가리키는지 확인했다.
- 실제 앱 테스트·빌드·브라우저/실기기 검증·실제 데이터 이전은 하지 않았다. A/B/G 인수 기준은 앞으로 구현에서 통과시킬 기준이다.
- 앱 소스 변경·추가 설치·원격 push·배포 없이 `docs/redesign/`의 문서와 시제품만 보완했다.
