## 1. 개발팀에 요청하는 내용

현재 앱을 **“현재 자산을 꾸준히 관리하고, 그 기록을 바탕으로 은퇴 후 생활과 미래 선택을 설계하는 도구”**로 보완해 주세요. 은퇴계획 미입력 상태에서도 시세 업데이트·계좌/종목 상세·평가 이력·배당 관리·백업을 사용할 수 있어야 합니다.

분석 페이지 일부의 디자인 변경이 아니라 **홈·자산·계획·분석·설정 및 연결된 상세·연금·법인 화면 전체**가 대상입니다. 첨부된 전체 화면 시제품을 UX 기준으로 삼되, 실제 저장 데이터와 정확한 계산 엔진에 연결해 주세요. 시제품을 별도 페이지로 붙이는 것만으로 완료 처리하지 마세요.

재건축은 여러 자산 상황 중 하나입니다. 부동산이 없는 사람, 일반 자가 보유자, 임대인·임차인, 재건축 보유자, 1인 가구와 이미 은퇴한 사람 모두 자신의 상황에 맞게 사용할 수 있어야 합니다.

기존 React·TypeScript·Vite·Dexie·PWA 구조와 사용자의 자산·이력·백업을 보존해 주세요. 서버 신설, 계좌 자동 연동, 프레임워크 전면 교체는 이번 필수 범위가 아닙니다.

## 4. 필수 개선 요구사항

### DEV-00. 현재 자산 관리를 독립된 핵심 기능으로 보존

- [07의 AM-01~AM-10](07-current-assets-and-retirement.md)을 기능 보존 체크리스트로 사용하세요. 주식 시세 갱신·계좌별 조회·종목 상세·가격/수량 이력·실제 배당·계좌 통합 모드·명의·환율·과거 보정 경로를 명시적으로 검수하세요.
- 홈에서는 현재 자산이 먼저 보이며, 은퇴 입력·계산 실패로 자산 조회와 갱신을 막지 마세요. 다른 자산 유형의 현재 관리도 보존하세요.
- 시세 갱신 실패는 이전 유효 값과 기준시각을 보존하고 부분 성공을 표시하세요. 가격 조회가 실제 수량·취득 원가·현금·배당 기록을 변경하면 안 됩니다.
- 관측/실적과 미래 가정을 분리하세요. 최신 현황으로 생성한 새 분석과 저장된 과거 분석을 구분하고, 시장 하락 대안이 현재 가격이나 과거 이력을 덮어쓰지 않게 하세요.
- 이전 코드의 평가 이력을 매매 거래원장으로 간주하지 마세요. 자료가 없는 실현손익·정밀 투자수익률은 새로 만들어 표시하지 마세요.

### DEV-01. 입력과 분석의 단일 원천

- 같은 자산·계좌·사람·계약·사건은 안정된 ID로 연결하고, 여러 페이지에서 같은 원천을 편집하게 해 주세요.
- 현재 자산 영역은 동일한 `assetRevision`으로 종목·계좌·전체 합계를 맞추고, 미래 전망 영역은 선택된 `snapshotId/runId`로 요약·상세·비교를 맞춰 주세요. 홈에 함께 표시할 때 두 영역의 기준일·버전을 구분하세요. 최신 시세가 저장돼도 고정된 과거 전망은 유지하고 새 현황으로 재계산할 수 있게 하세요.
- 화면별로 세금·연금·현금흐름을 따로 재계산하지 말고, 하나의 결과에서 요약과 상세를 조회해 주세요.
- 저장 실패 시 입력 초안을 보존하고 오류를 안내해 주세요. 부분 수정이 다른 설정을 지우지 않게 해 주세요. 늦게 끝난 이전 계산이 최신 결과를 덮어쓰면 안 됩니다.

### DEV-02. 은퇴 판단에 쓸 수 있는 월별 계산

- 기준일·계획 종료일을 입력받고, 기초 현금과 자산·부채를 반영해 월별 원장을 생성해 주세요. 시제품의 2030~2040년으로 고정하지 마세요.
- 외부 소득, 계좌 원금 인출, 내부 이체, 자산 매각, 차입, 원금 상환, 이자, 생활비와 세금을 구분해 주세요.
- 연금 계좌 지급은 실제 잔액을 초과할 수 없습니다. 지급 목표·실제 지급·미충당액을 따로 보여주고 수입 상세와 계좌 잔액을 일치시켜 주세요.
- 국민연금 등 지급권을 투자 원금으로 합산하거나 동일 연금을 두 번 수입에 넣지 마세요. 미래 목돈은 수령일부터 사용 가능해야 합니다.
- 수익률·물가·인출 정책의 기준일과 적용 순서를 명시해 주세요. 평가이익은 자동으로 생활 현금이 되지 않으며, 집을 자동 매각하거나 숨은 대출로 부족액을 메우지 마세요.
- 월평균 비용과 실제 납부월의 현금 유출을 구분해 주세요. 연간 세금·분담금·일회성 비용을 누락한 월수지를 전체 여유자금으로 제시하면 안 됩니다.

### DEV-03. 일반 부동산과 재건축의 날짜·상태 반영

- 일반 자가·임대·재건축/권리 상태와 시가·공시가격·과세 관련 값을 분리해 주세요.
- 준공, 사용승인 등 세무 판단에 필요한 사건, 입주, 임대 시작, 분담금, 임시 거주, 대출, 매각을 각각 관리해 주세요. 날짜를 연도까지만 아는 경우 임의의 확정일로 저장하지 말고 정밀도와 계산 가정을 표시해 주세요.
- 준공일에 연동한 임대 시작이나 비용 종료는 준공 변경 시 함께 이동하고, 계약상 고정일인 사건은 유지해 주세요. 변경 영향을 저장 전에 확인할 수 있게 해 주세요.
- **준공 전 모든 세금 0원 / 준공일부터 모든 세금 시작** 같은 단일 스위치를 사용하지 마세요. 공사 전후 상태·소유·과세 판단·귀속기간·납부 시점을 적용 가능한 규칙으로 구분해야 합니다.
- 임대인이 받은 보증금은 부채, 임차인이 낸 보증금은 자산으로 구분하고 수령·회수·반환을 연결해 주세요. 매각 후에도 남아 있는 세금 납부·정산 의무는 유지해 주세요.

검수 예: 준공 예정일을 2030년 9월에서 2031년 9월로 바꾸면, 준공에 연결된 임대 시작·임시 거주 종료 등은 이동하고 고정 분담금 일정은 유지되어야 합니다. 월별 현금흐름·세무 판단 입력·부족 시점의 변화 이유를 상세에서 설명할 수 있어야 합니다. 실제 세액의 기대값은 적용 규칙을 검증한 별도 fixture로 확인해 주세요.

### DEV-04. 사용자 상황에 따른 화면 노출

| 실제 입력 상태 | 보여줄 내용 | 노출하지 않을 내용 |
|---|---|---|
| 부동산 없음이 확인됨 | 금융·연금·생활비 중심 전망, 해당 시 임차 계약 | 보유 부동산의 준공·분담금·준공 지연 비교 |
| 일반 자가만 보유 | 주택 가치·주거비·대출·해당 세금 | 재건축 일정이나 임대 수입 자동 생성 |
| 임대 부동산 보유 | 임대 수입·보증금 반환·공실 대안 | 재건축 근거가 없는 준공 일정 |
| 재건축 자산 보유 | 해당 자산의 사업 단계·분담금·연결 일정·지연 대안 | 다른 일반 자산에 재건축 조건 일괄 적용 |
| 이미 은퇴한 1인 가구 | 본인 연금·인출·생활비 조정 | 배우자 입력 강요, 은퇴 연기 기본 추천 |
| 아직 입력하지 않음 | 필요한 입력과 부분 계산 가능 범위 | ‘보유 없음’ 단정, 0원 완성 결과, 은퇴 가능 결론 |

시제품의 ‘사용자 예시’ 선택기는 검토용입니다. 실제 제품에서 사용자를 하나의 유형으로 분류하도록 강요하지 말고, 복합 보유 상황에서 필요한 기능을 함께 제공해 주세요. 보유하지 않은 유형도 자산 추가에서는 등록할 수 있어야 합니다.

### DEV-05. 숫자를 누르면 이유와 원천까지 확인

- 핵심 금액에서 구성 내역 → 연도/월 → 거래 → 자산·사건·입력·산식·규칙으로 이동하게 해 주세요.
- 요약과 상세에 같은 기준일·시나리오·계산 버전을 사용하고, 합계가 맞아야 합니다.
- 예상값은 예상임을 표시하고, 누락값·확정 0·계산 실패를 구분해 주세요. 영향을 받는 지표와 입력 보완 경로를 제공해 주세요.
- 관련 원천을 수정한 후 같은 분석 문맥으로 돌아와 변경 전후 영향을 확인할 수 있게 해 주세요.
- 생활비 조정, 은퇴 시점 변경, 준공 지연 등은 실제 적용 가능한 대안만 제시하고, 바꾼 가정과 결과 차이를 함께 보여주세요. 소수 시나리오를 근거로 성공확률을 만들지 마세요.

### DEV-06. 세금·건강보험의 지원 범위와 신뢰성

- 적용연도·시행일·공식 근거·규칙 버전을 관리하고, 구현 시 공식 자료로 검증해 주세요. 이번 요청서는 세율이나 개인별 세액을 확정하지 않습니다.
- 개인별 귀속과 실제 가입·납부 단위를 반영해 주세요. 모든 가구를 부부 2명으로 가정하지 마세요.
- 원천징수와 추가 정산이 중복 차감되지 않도록 하고, 자동 추정과 수동 예상액의 적용 범위가 겹치면 명시적으로 대체해 주세요.
- 지원하지 않는 세무 사례는 ‘미지원/확인 필요’와 입력 방법을 제공해 주세요. 수동 금액에는 대상·기간·납부일·근거를 보관하고 미확정 비용을 0원으로 숨기지 마세요.
- 미래에는 현행 규칙 유지 등 어떤 가정을 사용했는지 표시해 주세요. 새로운 규칙 적용은 기존 결과를 덮어쓰기보다 비교 가능한 새 계산으로 관리해 주세요.

### DEV-07. 실제 저장·복원과 모바일 사용성

- 새로고침·앱 재실행 후 입력과 계획이 유지되어야 합니다. 예시 데이터와 실제 데이터를 분리해 주세요.
- 기존 데이터 변환 전 백업·변환 미리보기·검증을 제공하고, 실패 시 원본을 보존해 주세요. 의미가 불명확한 기존 미래연도를 재건축 준공으로 단정하지 마세요.
- 백업은 스키마·버전·필수 테이블·참조 관계를 검증한 뒤 원자적으로 복원해 주세요. 불완전한 파일로 먼저 전체 데이터를 지우면 안 됩니다.
- 모바일 390px 기준 주요 화면과 입력 폼에 불필요한 가로 넘침이 없어야 합니다. 버튼 터치 영역, 숫자 단위, 키보드 입력, 차트의 표 대체, 대화상자 초점·뒤로가기를 확인해 주세요.
- 개인정보·주소·자산 금액을 별도 동의 없이 외부로 전송하지 마세요.
- 기존 선택형 Google Drive 로그인·폴더 선택·저장·목록·복원·로그아웃 경로도 보존하세요. 로컬 백업만으로 대체 완료 처리하지 마세요. 기존 기능 구현 보존과 실제 사용자 계정 접속/업로드 실행 승인은 별개입니다.

## 5. 시제품에서 그대로 가져오면 안 되는 부분

시제품은 **화면과 흐름을 판단하는 합성 데이터 데모**입니다. 다음은 제품의 완료 상태가 아닙니다.

| 시제품의 단순화 | 제품 구현 요구 |
|---|---|
| 메모리에만 저장, 새로고침 시 변경 소멸 | 영구 저장·초안·오류 처리·revision 일관성 |
| 고정 기간, 물가·가격 상승 미반영 | 사용자 계획기간 및 명시된 성장·물가 가정 적용 |
| 세금·보험 고정 예상액, 세금 12월 일괄 예시 | 지원 규칙 또는 범위가 명확한 수동 예상액, 실제/가정 납부 일정 |
| 단순 이자와 임대 흐름 | 원리금 상환·보증금 정산·매각·소유 기간까지 연결 |
| 현재 자산 표시와 단순 생활 현금 전망 | 월별 잔액에 근거한 미래 자산·부채·인출 가능액 대사 |
| 법인 세전 구조 미리보기 | 법인·개인 간 자금 및 세금·비용 검증. 미지원이면 부분 결과로 격리 |
| JSON 내보내기와 복원 화면 미리보기 | 실제 백업 읽기·사전 검증·복원·실패 복구 |

## 6. 적용 순서와 작업 단위

각 단계는 구현 코드·테스트·데이터 호환성·확인 가능한 화면을 함께 제출해 주세요. 화면은 전체 범위로 설계하되, 적용은 R0 이후 기존 R1~R6 순서로 진행해 주세요. 현재 자산 관련 단계별 보완은 07의 7절을 함께 적용하세요.

| 단계 | 요청 작업 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| R0 현재 기능 기준선 | AM 목록의 기존 동작·데이터·대체 위치·회귀 검사 확보 | 은퇴 미입력 사용 사례 확인, 새 화면 미완성 시 기존 전문 화면 접근 보존 |
| R1 정확성·저장 복구 | F01 국민연금 중복, F02 설정 유실, F03 잔액 초과 지급, F08 배당 세금 중복 우선 재현·수정 | 올바른 기대값의 회귀 테스트, 잔액과 현금 유입 일치, 다른 입력 보존 |
| R2 단일 원천·상태 | 사람·계좌·자산·계약·사건 ID, 입력 완료 상태, 준비 상태, revision, 조건부 기능 | 복합 자산·무부동산·1인·미입력 상태를 정확히 구분 |
| R3 공통 은퇴 엔진 | 현금·투자·연금·생활비·원장·원천 추적 | 부동산 없는 사람도 입력부터 상세까지 사용 가능, G 사례 검증 |
| R4 부동산·부채 | 일반 주거·임대·재건축·대출·보증금·매각 사건 | 날짜 연동과 고정일 구분, 잔액·현금·관련 규칙 입력 대사 |
| R5 전체 화면 전환 | 위 대응표 전 페이지, 상세 이동, 비교, 반응형·접근성 | 현재 영역의 합계 일치, 선택 전망 영역의 요약/상세 동일 run, 실제 저장/재조회, 이전 링크 대응 |
| R6 안전한 전환 준비 | 이전·복원·PWA 업데이트·운영 안내·미지원 범위 정리 | 원본 보존·복구 테스트·실기기 검수, 출시 전 승인 가능 상태 |

현행 결함 목록은 정적 코드 검토에서 나온 근거입니다. 실행 환경에서 먼저 재현하고 테스트로 확인해 주세요. 기준 커밋 이후 코드가 달라졌다면 적용 위치와 이미 해결된 항목을 기록해 주세요. `verify-baseline.cjs`는 기존 결함 관찰 보조 자료이며, 잘못된 기존 결과를 유지하기 위한 정답 테스트가 아닙니다.

## 7. 완료 검수와 개발 결과물

[04의 A01~A30](04-delivery-and-acceptance.md), [05의 B01~B24·G01~G06](05-implementation-spec.md), [07의 C01~C29](07-current-assets-and-retirement.md)을 테스트 목록으로 사용하세요. 특히 은퇴 입력 없이 시세 갱신 → 계좌 → 종목 → 이력/실제 배당 확인과 시나리오 변경 후 실제 기록 불변을 검수하세요. 다음 사용자 흐름도 실제 제품에서 확인해 주세요.

1. 부동산 없이 현금·연금·생활비를 입력 → 저장 → 재실행 → 홈·분석·월 상세의 금액 일치 확인.
2. 일반 자가 추가 → 주택·대출 반영 확인 → 재건축 카드·준공 지연 비교가 없는지 확인.
3. 재건축 추가 후 준공 변경 → 연결 일정 이동·고정일 유지 → 현금 부족 시점과 세금 관련 변화 근거 확인.
4. 생활비 수정 → 새 결과 반영 → 숫자 선택 → 월 거래·원천 확인 → 뒤로가기로 분석 문맥 복원.
5. 연금 계좌 소진 → 실제 지급 제한·미충당액 표시 → 같은 월의 수입 상세와 계좌 잔액 일치 확인.
6. 미입력·조회 실패·저장 충돌 → 낙관적인 0원 결과를 만들지 않고 누락/오류·초안을 보존하는지 확인.
7. 대안 편집 → 기본안 입력 보존 → 차이 설명 → 적용 시 명시적 확인과 새 revision 생성 확인.
8. 기존 백업 이전·복원 및 잘못된 파일 복원 실패 → 자산·명의·이력·참조 관계와 원본 보존 확인.

단계별 인계에는 다음을 포함해 주세요.

- 완료한 R 단계와 DEV 요구사항, 변경 파일, 실제 실행한 테스트·빌드 결과와 미실행 항목.
- 요구사항 ↔ 구현 위치 ↔ 테스트 ID의 대응표. 미완료는 이유·영향·다음 작업을 명시.
- 기존 페이지별 개편 화면 캡처와 실행 방법. 모바일·데스크톱에서 전체 흐름을 판단할 수 있는 검수본.
- 데이터 스키마 변경, 이전/복원 절차, 실패 복구 방법, 지원·미지원 계산 범위.
- 계산 정답 fixture와 기대값, 원천·상세 합계 검증 결과. 실제 세무 규칙 테스트는 합성 현금흐름 테스트와 구분.

시제품의 기존 브라우저 확인 기록은 제품의 계산 정확성·테스트·빌드 통과를 의미하지 않습니다. 최종 검수는 **실제 앱에 적용된 기능**으로 수행해 주세요. 미지원 기능을 숨긴 채 전체 완료로 보고하지 말고, 단계별 범위와 남은 작업을 명시해 주세요.

## 8. 작업 권한과 별도 협의 사항

이 요청서는 개발 구현을 위한 인계 자료이며, 이번 문서 작성 과정에서 실제 앱 소스·개인 데이터·원격 저장소를 변경한 것은 아닙니다. 개발 시 기존 사용자 변경을 보존하고 저장소 작업 지침을 따라 주세요.

현재 요청자 환경은 추가 설치 없이 검토하기로 한 상태입니다. 이 환경의 의존성 설치·환경 변경이 필요하면 필요와 범위를 먼저 설명하고 승인을 받아 주세요. 원격 push·배포·실제 개인 데이터 이전·외부 서비스 연동은 별도 승인 없이 진행하지 마세요.

파일 구조나 컴포넌트 분할 같은 일반 구현 결정은 개발팀에서 진행하되, 기존 기능 제거·계산 지원 범위 축소·데이터 의미 변경은 사용자에게 영향과 대안을 설명한 뒤 합의해 주세요.
