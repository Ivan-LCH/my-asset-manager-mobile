# 10. 실제 이전 백업으로 수행한 화면·연결 검증

**후속 상태:** 아래는 수정 전 발견 기록이다. 사용자의 적용 요청에 따라 8건을 보완했다.
현재 적용 내용과 재검증 결과는 [11. 보완 적용](11-review-fixes-applied.md)을 먼저 읽는다.

검증일: 2026-09-15. 기존 설계, 현재 코드, 사용자 제공 백업을 복원한 별도 브라우저를 대조했다.
이 문서는 **검증 결과와 보완 명세**다. 아래 화면 문제를 이미 수정했다는 완료 보고가 아니다.

## 결론

사용자가 지적한 ‘자산 전체에서 주식이 계좌별로 묶이지 않는 문제’는 재현되었다.
현재 화면은 소수 합성 자산에서는 열리지만 실제 보유 규모에서 요약→상세 구조가 무너진다.
연금 원천 연결과 기존 계산 표시에도 중요한 불일치가 있다. 개인별 최종 인수 테스트 전에
아래 P1 항목을 먼저 보완해야 한다. 147개 테스트 통과는 이 UX 인수 항목의 통과를 의미하지 않는다.

## 확인 범위와 데이터 보호

- 실제 가져오기 컨트롤에 파일을 넣고 확인 대화상자를 거쳐 복원했다.
- 전체 자산 54행 중 현재 보유 52행, 주식 35행/4개 계좌, 이력 7,016행을 가진 데이터다.
- 홈, 자산 6개 보기, 이력, 계획 6개 탭, 새 분석, 기존 참고 분석 5개 탭, 설정의
  **21개 경로를 PC 1440px와 모바일 390px에서 각각 확인**했다.
- 데이터에 있는 주식·부동산·예적금·연금·실물의 직접 상세 5개와 주식 배당 탭을 추가 확인했다.
  비동기 데이터 로딩이 끝난 뒤 수정 버튼/배당 내역과 모바일 너비를 검사했다.
- 실제 데이터의 원본 테이블은 복원 직후와 화면 재방문 후 같았다. 기존 파일을 수정하지 않았다.
- 개인 자산 이름·금액·계좌명은 보고서/fixture에 싣지 않고 실제 화면 캡처도 저장하지 않았다.
  임시 프로필은 검사 후 삭제한다. 사용자 평소 브라우저, 실제 시세, Google 계정은 변경하지 않는다.
- 실제 금융 데이터를 편집·삭제하거나 모든 금융 시나리오를 최종 확정한 검사는 아니다.
  등록/수정의 모든 버튼과 실기기 PWA 검수는 별도 인수 범위다.

## 발견 사항

### UI-01 · P1: 자산 전체가 요약이 아닌 전 항목 나열

- **재현:** `/assets?type=ALL`에 개별 자산 링크 52개, 패널 53개(요약 1 + 자산 52)가 있다.
  주식은 계좌 4개인데 종목 35개가 다른 자산과 같은 층위에서 모두 펼쳐진다.
  모바일 본문 높이는 약 10,208px로 실제 본문 뷰포트(789px)의 약 13배다.
- **원인:** `CurrentAssetsOverview`가 `current.positions.map(...)`으로 직접 카드를 만든다.
  계좌/유형 집계와 접기 상태가 없다. 반면 주식 전문 화면은 계좌 카드 4개부터 보여준다.
- **보완:** 전체는 유형별 요약을 우선하고 주식은 계좌별 평가액·보유 종목 수로 묶는다.
  계좌를 누르면 해당 계좌의 종목 관리로 들어가며 전체 화면에서 모든 종목을 펼치지 않는다.
  보기만 그룹화하고 실제 종목·배당·이력 데이터는 유지한다.
- **인수:** 이 데이터에서 전체 화면의 초기 주식 항목은 4개 계좌 단위다. 합계는 종목 원천과
  일치하고, 계좌를 펼치거나 이동했을 때 35개 종목을 빠짐없이 조회할 수 있어야 한다.
- **코드:** `frontend/src/planner/pages.tsx:81`, `frontend/src/pages/StockPage.tsx:122`.

### DATA-02 · P1: 연결 연금의 인출 원천이 실제 주식계좌를 따르지 않음

- **재현:** 기존 연금 2건은 주식 계좌명으로 연결되어 있다. 해당 주식계좌에는 잔액이 있으나
  연금 레코드 자체 잔액은 0이다. 새 ‘자산에 등록한 연금 지급액 연결’ 미리보기는 양수 인출
  2건의 `assetId`를 실제 주식계좌가 아닌 그 0원 연금 레코드로 설정한다.
- **원인:** 기존 `linkedStockId`는 이름과 달리 **계좌명**이다. 새 정책의 `linkedTo`는 개별 자산 ID라
  의미가 다르다. `assetFlowPreview`는 지급액의 원천과 출금 잔액의 원천을 같은 자산으로 취급한다.
- **영향:** 연결 계좌가 살아 있어도 이대로 인출 조건을 완성하면 연금 인출이 잔액 부족으로
  제한될 수 있다. 이번 파일에서 이 연금 원금의 이중 가산은 발견하지 않았다. 문제는 출금 연결이다.
- **보완:** 지급액 원천과 출금 계좌를 분리한다. 기존 계좌명→계좌 ID/보유 종목 묶음을 확인하는
  이전 미리보기를 제공하고, 계좌 내 인출 순서·제한·잔액 한도를 명시한다. 주식계좌 잔액을
  연금 레코드에 복사해 원금을 이중 생성하거나 임의로 첫 종목만 출금 대상으로 삼으면 안 된다.
- **인수:** 별도 합성 사례로 연결 계좌의 순액 인출과 잔액 감소를 확인하고, 계좌 전체 잔액
  소진 후에만 미충족을 표시한다. 계좌명 변경 후에도 연결이 유지되어야 한다.
- **코드:** `frontend/src/planner/storage.ts:102`, `frontend/src/planner/model.ts:100`,
  `frontend/src/lib/db.ts`의 `renameStockAccount`.

### DATA-03 · P1: 연금 자산 화면에 별도 미래 계산이 계속 노출

- **확인:** 자산→연금의 ‘은퇴 시 월 수령/최대 월 수령’은 새 월별 원장이 아니라
  `PensionPage.buildSimulation`에서 계산한다. 여기서는 등록 월 지급액과 연도 구간을 더하고,
  인출 계좌 소진이나 새 계획의 월별 조건을 같은 방식으로 반영하지 않는다.
- **영향:** 새 분석을 믿어야 한다고 안내하면서 일상 자산 관리 화면에서는 다른 방식의 미래
  수령액을 보여준다. `/legacy-analysis`를 분리한 것만으로 모든 구 계산이 격리된 것은 아니다.
- **보완:** 자산 화면은 현재 연금 계약/등록 지급 목표임을 표시하고 미래 예측과 구분한다.
  미래 수령 전망을 표시하려면 저장한 새 분석의 동일 사본·버전에서 읽는다. 구 방식은
  참고 표시와 한계를 명확히 붙이거나 참고 경로로 옮긴다.
- **인수:** 같은 사본·연도·월에 표시된 연금 실지급액이 새 분석 상세와 일치해야 한다.
  등록 목표액은 실지급 전망과 별도 라벨이어야 한다.
- **코드:** `frontend/src/pages/PensionPage.tsx`의 `buildSimulation`, `pensionLikeAssets`, 연금 KPI.

### UI-04 · P1: 자산 연결 편집이 실제 규모를 감당하지 못함

- **재현:** `/plan?tab=policies`에 52개 패널과 입력/선택 컨트롤 466개가 처음부터 펼쳐진다.
  모바일 본문은 약 45,022px(본문 뷰포트의 약 57배)다. 모든 항목이 분류 미확인으로 시작한다.
- **영향:** 계좌 단위로 같은 조건을 입력하기 어렵고 확인해야 할 예외와 일괄 적용할 조건을
  구분할 수 없다. 가로 넘침이 없다는 이유로 사용하기 좋은 화면이라고 판단할 수 없다.
- **보완:** 유형/계좌별 접기, 이름 검색, 미확인만 보기, 선택 자산의 상세 편집을 제공한다.
  계좌 단위 공통 조건은 변경 내역 미리보기 후 적용하고 종목별 예외는 유지한다.
  금액·세율·명의를 확인 없이 일괄 확정하지 않는다.
- **인수:** 첫 화면은 그룹 요약이며 입력 폼은 선택한 자산/계좌에 대해서만 열린다.
  원천 링크를 누르면 해당 그룹이 펼쳐지고 대상 입력에 초점이 이동한다.
- **코드:** `frontend/src/planner/pages.tsx:136`, `frontend/src/planner/pages.tsx:155`.

### UI-05 · P2: 계좌 선택 문맥이 새로고침/다른 화면 이동에서 사라짐

- **재현:** 주식 계좌 카드 클릭은 성공하지만 주소에 계좌가 기록되지 않는다.
  같은 주소를 새로 열면 선택 계좌가 아닌 전체 계좌 목록으로 돌아간다.
- **원인:** `activeAccount`와 종목 모달 선택이 컴포넌트 로컬 상태다.
  직접 자산 상세의 복귀 링크도 유형만 지정하고 출발 계좌/필터를 보존하지 않는다.
- **보완:** 계좌·선택 종목·복귀 문맥을 URL의 안정된 ID로 표현한다. 브라우저 뒤로가기와
  화면 내 뒤로가기, 새로고침의 동작을 통일한다.
- **인수:** 전체→특정 계좌→종목→계획 원천→뒤로가기에서 계좌와 검색/스크롤 문맥을 보존한다.
- **코드:** `frontend/src/pages/StockPage.tsx:46`, `frontend/src/planner/pages.tsx:88`.

### UI-06 · P2: 백업 복원 뒤 ‘보존된 입력’과 ‘새 계획에 적용된 입력’의 구분이 약함

- **확인:** 구 백업에는 부부 생년월·계좌 명의·은퇴계획이 있지만 새 계획은 본인 1명의 빈
  기본값에서 시작한다. 기존 계획 미리보기에서도 사람은 1명이며, 일부 정기 항목/목돈만 복사한다.
  새 분석에는 아직 결과가 없고 기본 화면은 첫 계획 입력을 안내한다.
- **판단:** 원본 소실은 아니다. 불명확한 법인·여행·보험 조건을 자동 확정하지 않은 선택은
  유지해야 한다. 다만 사용자는 복원 성공 후 이미 입력했던 사항이 사라졌다고 느끼기 쉽다.
- **보완:** 복원 완료 후 ‘원본 복원 완료 / 새 계획 연결 대기’를 구분한 이전 점검 화면을 제공한다.
  기존 가구/명의 매핑, 복사 가능 항목, 의미/날짜 확인 필요 항목, 아직 지원하지 않는 항목을
  건수와 원본 바로가기로 보여준다. 확인한 정보만 새 계획에 반영한다.
- **인수:** 사용자가 새 화면에서 미반영 이유와 확인해야 할 원본을 찾을 수 있어야 한다.
  기존 배우자/공동 명의를 조용히 본인 단독 명의로 확정하면 안 된다.
- **코드:** `frontend/src/planner/storage.ts`의 `loadContext`, `legacyPreview`,
  `frontend/src/planner/model.ts`의 `blankPlan`.

### UI-07 · P2: ‘연금 시뮬레이션’ 동작과 도착 화면 의미 불일치

- **실제 클릭·코드 확인:** 연금 자산 화면의 ‘시뮬레이션’ 버튼은 `/pension/sim`을 연다.
  현재 라우터는 이를 `/plan?tab=flows`로 바꾼다. 버튼 이름과 달리 결과/시뮬레이터가 아니라
  정기 입출금 편집 화면으로 이동하며 선택 연금 문맥도 전달하지 않는다.
- **보완:** ‘지급 계획 연결’이면 해당 문구와 원천 연금을 전달한다. ‘분석 보기’이면 해당 연금의
  저장 분석/월별 인출 내역으로 이동하고, 결과가 없으면 필요한 연결 단계부터 안내한다.
- **인수:** 버튼 이름·도착 화면 제목·선택 연금의 문맥이 일치해야 한다.
- **코드:** `frontend/src/pages/PensionPage.tsx`, `frontend/src/App.tsx:43`.

### UI-08 · P2: 모바일 기존 현금흐름 본문 가로 넘침

- **재현:** 390px의 `/legacy-analysis?tab=cashflow`에서 본문 `main.scrollWidth`가
  `main.clientWidth`를 초과한다. 문서 루트의 가로 너비 검사만으로는 발견되지 않는다.
- **보완:** 긴 표는 표 전용 스크롤 영역으로 제한하고 요약/버튼이 본문 전체를 넓히지 않도록 한다.
  향후 모바일 검사는 문서 루트뿐 아니라 실제 스크롤 컨테이너도 검사한다.
- **인수:** `main`은 가로로 넘치지 않고, 필요한 표 안에서만 가로 스크롤할 수 있어야 한다.

## 보완 순서

1. DATA-02의 실제 인출 원천 연결과 DATA-03의 미래 계산 표시 분리를 먼저 처리한다.
2. UI-01 전체 자산 그룹화와 UI-04 계좌별/선택형 계획 편집을 함께 맞춘다.
3. UI-05 문맥 보존, UI-06 이전 확인, UI-07 버튼 의미, UI-08 모바일 넘침을 정리한다.
4. 동일 파일로 재검증한 뒤 사용자의 최종 인수 테스트를 진행한다.

최종 사용자 테스트는 시세 갱신→계좌 상세→배당/이력→자산 편집→새 계획 연결→연금/부동산
일정→분석 원천 확인→백업 재복원 순서가 적합하다. 실제 시세 공급자/Google 인증은 별도다.

## 확인한 정상 범위

- 구 백업 취득일 `null` 호환 결함은 수정했다. 원본 전체 테이블 및 v2 재복원 보존 확인.
- 호환성 수정 후 147개 테스트와 제품 빌드 통과.
- 주식 전문 화면의 계좌 4개 그룹 및 선택 후 종목 목록은 동작한다.
- 점검한 주요 경로들은 열리며 위 현금흐름 참고 화면을 제외하면 측정 시 `main` 가로 넘침은 없었다.
- 현재 자산 관리에 접근하려고 새 은퇴계획을 먼저 저장할 필요는 없다.

재현 명령: `node tools/check-local-app.cjs --backup <개인 백업 경로> --review`.
연결 점검: `node tools/check-backup-compat.cjs <개인 백업 경로> --audit`.
두 도구는 개인 데이터의 값 대신 구조/건수/참조 상태만 출력한다.
